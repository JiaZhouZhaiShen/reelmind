## 二、修正方案（按严重度）

### 🔴 问题 2（最高优先）：check.sh Windows 失效 → 加工具自检

**做什么**：
1. `scripts/check.sh` 开头加**工具前置检查**：`grep/awk/find/tr/xargs/sed/sort/head/wc/git/docker` 任一不可用 → 直接失败退出（`exit 2` 并提示"运行环境缺工具，请用 Git Bash 完整环境"），禁止静默全绿。
2. `hooks/pre-commit` 开头同样自检，或复用 check.sh 的前置检查。
3. 修订记录补一条：历史"全量通过"结论在 Windows 非登录 shell 下不可信，需在完整 Git Bash 重跑确认基线。

**不做什么**：不改 Windows PATH 本身、不改为纯 PowerShell 实现。

**涉及文件**：`scripts/check.sh`、`hooks/pre-commit`
**验收**：`env -i PATH=/usr/local/sbin bash scripts/check.sh` 必须失败（exit 2），完整 PATH 下正常。

### 🔴 问题 1：R4.2 规则与实现矛盾 → 规则修订（推荐）或代码改造（可选）

**矛盾本质**：规则写"查 SQLite 实际记录数"，实现是"查 PG status"。后端注释给出理由：OCR 可能合法产生零结果（视频无文字），用 SQLite 存在性判断会把"跑完但零结果"误判为"未完成"。

**推荐方案（规则修订，本方案范围）**：
- 修订 `docs/铁律.md` R4.2 为：**"展示依赖 results_ready：前端不直接读引擎 status，一律用后端 results-ready 出口；results_ready 的具体判定（查实际数据 or 结合 status）由后端负责并如实记录"**。
- 同步修订 `docs/规范/04_调度规范.md`：如实描述当前实现（PG status 判定 + 零结果合法场景），删除"已符合"的失实表述。
- 这样规则与实现一致，且保留"前端不依赖 status"的核心约束。

**不做什么（超边界，另行立项）**：不改 `pipeline.py` 的判定逻辑、不做"真查 SQLite"改造。

**涉及文件**：`docs/铁律.md`、`docs/规范/04_调度规范.md`
**验收**：规则文字与 pipeline.py 注释逻辑一致；规范不再声称"已符合 SQLite 判定"。

### 🔴 问题 3：R1.1 检查范围扩大 → 覆盖 server/app/ml 死代码

**做什么**：`scripts/check.sh` R1.1 检查范围从 `server/app/api/` 扩为 `server/app/`（含 `server/app/ml/`）。检查到 `import torch` 即违规——当前 `clip_embedder.py`、`whisper_transcriber.py` 会立即暴露。

**不做什么**：不删 ml 死代码（属代码侧待办，另行确认）。

**涉及文件**：`scripts/check.sh`
**验收**：全量 check.sh 新增 R1.1 违规，精确列出 ml 两个文件。

### 🟡 问题 4：工具命令补全 → 脚本纳入 package.json

**做什么**（二选一，需确认）：
- **方案 A（推荐）**：`web/package.json` scripts 加 `"typecheck": "tsc --noEmit"`（无需新依赖，tsc 已由 typescript 提供）；规范中 `pnpm typecheck` 改为 `npm run typecheck` 或统一 `pnpm`（项目用 pnpm-lock）。
- **方案 B**：只改规范，把 `pnpm typecheck` 换成实际可跑的 `npm run build`（含 tsc -b），不新增脚本。

**涉及文件**：`web/package.json`、`docs/规范/00_工作流程.md`、`docs/规范/02_前端规范.md`
**验收**：规范中引用的命令实际可执行；typecheck 有真实入口。
