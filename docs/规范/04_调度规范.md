# 04 调度规范

> 对应铁律：R4.1-R4.2
> 作用：AI 管道调度（Server / Orchestrator / AI Worker）的状态与结果边界。

---

## R4.1 状态与结果分离

**边界**：

| 数据 | 存哪里 | 用途 |
|------|--------|------|
| `processing_state`、`ai_engine_jobs.status` | PG | 调度、进度、重试 |
| 场景帧、标签、OCR、字幕 | SQLite | 前端展示、搜索 |
| CLIP 向量 | PG (pgvector) | 语义搜索 |

**原则**：状态驱动调度，结果驱动展示。两者不混、不双写。

## R4.2 展示依赖 results_ready

**边界**：前端不直接读引擎 `ai_engine_jobs.status`，一律通过后端 `results-ready` 出口获取展示依据。

```json
GET /api/media/{id}/status
{
    "state": "completed",
    "results_ready": { "scenes": true, "ocr": false, "subtitle": true, "tags": true }
}
```

**原因**：status 表示"引擎跑没跑完"，results_ready 表示"结果是否可展示"。前者不等于后者（如引擎完成了但结果为空）。

**实现现状（2026-09-02 实测）**：`server/app/api/ai/pipeline.py` 的 `get_results_ready()` 当前用 **PG 中 `ai_engine_jobs.status == 'completed'`** 判定 results_ready（代码注释理由：OCR 等引擎可能合法产生零结果，用 SQLite 存在性判断会把"跑完但零结果"误判为"未完成"）。该函数 docstring 声称"based on actual SQLite data"与实现不符，属文档失实——**判定方式由后端负责并须如实记录，前端只消费 results-ready 出口，不直接读 status**。

> 说明：R4.2 规则已按此修订（铁律本体第 2026-09-02 修订）。若未来要求"按实际数据存在性判定"，属后端改造，另行立项。
