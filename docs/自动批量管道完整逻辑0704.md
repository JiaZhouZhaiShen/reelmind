# 自动批量管道完整逻辑

> 记录时间：2026-07-04
> 涉及服务：reelmind-server、reelmind-orchestrator、reelmind-ai

---

## 一、整体架构

```
┌─ 手动批量 ─────────────────────────────────────────┐
│                                                     │
│  UI 点"开始批量"                                    │
│    → POST /ai/pipeline/manual/start                  │
│      → _orchestrate_batch("manual", ...)  (Server)   │
│        → start_pipeline() → AI 容器                  │
│        → wait_for_completion()                       │
│                                                     │
└─────────────────────────────────────────────────────┘

┌─ 自动批量 ─────────────────────────────────────────┐
│                                                     │
│  Orchestrator (_run_loop)                           │
│    ├─ GET  /ai/pipeline/auto/config                 │
│    ├─ GET  /ai/pipeline/auto/pending-summary         │
│    ├─ GET  <AI>/health         (GPU 检查)            │
│    ├─ POST /ai/pipeline/auto/claim                   │
│    │   └─ Server: FOR UPDATE SKIP LOCKED + 写事件    │
│    ├─ loop: GET /ai/pipeline/auto/chunk-done         │
│    └─ done → 下一轮                                  │
│                                                     │
│  Server (event_scanner 后台线程)                     │
│    └─ 轮询 orchestration_events 表                   │
│      → 读到 chunk_ready                             │
│      → _orchestrate_batch("auto", media_ids)         │
│        → start_pipeline() → AI 容器                  │
│        → wait_for_completion()                       │
│                                                     │
└─────────────────────────────────────────────────────┘
```

## 二、设置保存链路

| 环节 | 组件 | 文件/函数 | 动作 |
|---|---|---|---|
| **① UI 保存** | 前端 | `AIPipelineConfig` / `AutoRunStatus` | 用户改配置 → 调 `POST /api/ai/pipeline/auto/config` |

| 存储 | 容器内路径 | 本机路径 |

`get_auto_config()` → **① PG 查询** → 有数据则返回 → **② JSON 文件**（PG 失败或无数据时回退）

## 三、配置参数全映射

| 参数 | 类型 | 默认值 | 在 Orchestrator 中哪使用 |
|---|---|---|---|
| `enabled` | bool | `false` | `_check_auto_conditions()` — 第一关判断 |
| `engines` | string[] | `["scene","yolo","ocr","clip","transcript","diarization"]` | 传给 claim API，Server 按引擎筛选 |
| `batch_size` | int | `50` | 传给 claim API，SQL 中作为 LIMIT |
| `time_window_start` | int | `0` | `_check_auto_conditions()` — 时区感知检查 |
| `time_window_end` | int | `6` | `_check_auto_conditions()` — 时区感知检查 |
| `gpu_threshold_percent` | int | `50` | `_check_auto_conditions()` — 直调 AI `/health` |
| `check_interval_seconds` | int | `60` | `_run_loop()` — 轮询间隔，覆盖默认 5s |
| `timeout_minutes` | int | `180` | `_run_auto_schedule()` — chunk 等待超时 |
| `filters.max_file_size_mb` | int | `0` | claim API SQL 中过滤大文件 |
| `filters.max_duration_minutes` | int | `0` | claim API SQL 中过滤长视频 |

> 设置改变**不需要重启任何容器**。Orchestrator 和事件消费者都不缓存配置，每次读取从 PG 拿最新值。

## 四、主调度循环（Orchestrator 容器内）

```
┌─ _run_loop() ─────────────────────────────────────────────────────────┐
│                                                                        │
│  1. _recover_stale()                                                   │
│     → POST /api/ai/pipeline/auto/recover-stale                         │
│       ├  running 超时且未达 max_retries → 回退 pending + 重试计数 +1    │
│       └  running 超时且已达 max_retries → 标记 error                    │
│                                                                        │
│  2. _log_pending_summary()                                             │
│     → GET /api/ai/pipeline/auto/pending-summary                        │
│       └ 返回 {backlog, running, total_pending, pending_per_engine}     │
│                                                                        │
│  3. if pending > 0 → _run_auto_schedule()                              │
│        │                                                               │
│        ├─ 3a. _get_auto_config()  (读取配置)                           │
│        │                                                               │
│        ├─ 3b. _check_auto_conditions(config)                           │
│        │   ├  enabled == true ?                                        │
│        │   ├  time_window_start ≤ 当前小时 < time_window_end ?          │
│        │   ├  backlog > 0 ?  (通过 pending-summary API)                 │
│        │   ├  running == 0 ?  (通过 pending-summary API)                │
│        │   └  GPU 使用率 < gpu_threshold_percent ?  (直调 AI /health)  │
│        │                                                               │
│        └─ 3c. while True (一次循环处理一个 chunk)                       │
│             ├  POST /ai/pipeline/auto/claim                            │
│             │  └ Server: FOR UPDATE SKIP LOCKED → running + 写事件     │
│             ├  轮询 GET /ai/pipeline/auto/chunk-done (每 10s)           │
│             │  └ Server: 查 ai_engine_jobs 该 batch 完成状态            │
│             ├  chunk 完成 → 检查下一 chunk                              │
│             ├  chunk 超时 → POST /ai/pipeline/auto/reclaim              │
│             │  └ Server: running → pending 回退                        │
│             └  条件不再满足 → 退出循环                                   │
│                                                                        │
│  4. time.sleep(check_interval_seconds)                                 │
│     (默认 60s，从最新配置读取，覆盖 env 默认 5s)                        │
└────────────────────────────────────────────────────────────────────────┘
```

### Orchestrator 调用的 API 端点

| 步骤 | API 端点 | 方法 | 效果 |
|---|---|---|---|
| recover | `/ai/pipeline/auto/recover-stale` | POST | 超时 jobs → pending/error |
| summary | `/ai/pipeline/auto/pending-summary` | GET | 返回各引擎待处理数 |
| config | `/ai/pipeline/auto/config` | GET | 读取用户保存的完整配置 |
| claim | `/ai/pipeline/auto/claim` | POST | 原子取 chunk → running + 写 `chunk_ready` 事件 |
| poll | `/ai/pipeline/auto/chunk-done?batch_id=xxx` | GET | 查 chunk 是否处理完 |
| reclaim | `/ai/pipeline/auto/reclaim` | POST | 超时回收 → running 回退 pending |

## 五、AI 执行链路（Server 内的事件消费者）

Orchestrator claim chunk 时写 `chunk_ready` 事件 → Server 的事件消费者拾取并调度到 AI：

```
┌─ start_event_scanner() 后台线程 (每 5s 轮询) ──────────────────────────┐
│                                                                        │
│  1. 查 orchestration_events                                            │
│     WHERE event_type='chunk_ready' AND consumed=false                  │
│     ORDER BY id LIMIT 5                                                │
│                                                                        │
│  2. 标记 consumed = True，提交事务                                      │
│                                                                        │
│  3. 读 auto_config = get_auto_config()  (从 PG，每次新鲜读取)           │
│     ├ enabled == false → 跳过（打日志跳过信息）                          │
│     └ enabled == true → 继续                                           │
│                                                                        │
│  4. 启动后台线程: _orchestrate_batch("auto", config, None, media_ids)   │
│     ├ 获取 _orchestration_lock（同一时间只有一个 in-flight）             │
│     ├ 创建 BatchCheckpoint                                             │
│     ├ for each chunk of batch_size:                                    │
│     │   ├ start_pipeline(media_ids) → AI 容器 /pipeline/start           │
│     │   └ wait_for_completion() → Redis pub-sub 进度通知                │
│     └ 更新 checkpoint.processed                                        │
│                                                                        │
└────────────────────────────────────────────────────────────────────────┘
```

### 两个并行的等待机制

| 谁在等 | 怎么等 | 等什么 |
|---|---|---|
| Orchestrator | 每 10s 调 `chunk-done` API 查 `ai_engine_jobs` 表 | 等 DB 状态全部完成 |
| Server (event scanner) | Redis pub-sub 实时推送 | 等 AI 容器的 pipeline 进度通知 |

> 它们等的是一件事（chunk 处理完），只是角度不同。Orchestrator 查 DB，Server 等实时推送。

### 互斥保证

手动和自动最终汇聚到同一个入口：`_orchestrate_batch()`（`shared.py`）。

```
if not _orchestration_lock.acquire(blocking=False):
    logger.warning("另一个 orchestration 正在运行，跳过")
    return None
```

| 触发方式 | 路径 | 锁 |
|---|---|---|
| 手动点击批量 | `start_manual_batch()` → thread → `_orchestrate_batch("manual")` | `_orchestration_lock` |
| 自动事件消费 | `start_event_scanner()` → thread → `_orchestrate_batch("auto")` | `_orchestration_lock` |

## 六、设置变更响应

| 修改场景 | 生效时机 | 机制 |
|---|---|---|
| 修改 `enabled`（开/关） | 下一轮 Orchestrator 循环 | `_check_auto_conditions()` 读最新配置 |
| 修改 `engines` | 下一次 claim chunk | `_run_auto_schedule()` 传最新 engines 给 claim API |
| 修改 `batch_size` | 下一次 claim chunk | claim API 用新 batch_size 做 LIMIT |
| 修改 `time_window` | 下一轮条件检查 | `_check_auto_conditions()` 用新窗口比较当前小时 |
| 修改 `gpu_threshold` | 下一轮条件检查 | `_check_auto_conditions()` 用新阈值比较 GPU |
| 修改 `filters` | 下一次 claim chunk | claim API 的 SQL 用新过滤条件 |
| 修改 `check_interval_seconds` | 下一轮 sleep | `_run_loop()` 读最新配置后用它做 sleep |
| 修改 `timeout_minutes` | 下一次 wait | `_run_auto_schedule()` 用新 timeout 算 deadline |
| **正在处理中修改** | **不影响当前 chunk** | 当前 chunk 用 claim 时的配置；下一 chunk 用新配置 |

## 九、超时回收流程

```
Orchestrator claim chunk 后等待完成
  │
  ├─ deadline 内 chunk 未完成
  │     │
  │     ├─ 检查服务存活 (Server ping + AI health)
  │     │   ├ 存活 → 继续等待（每 10s 检查一次）
  │     │   └ 连续 2 次不可达 → 放弃等待
  │     │
  │     └─ 超时 (timeout_minutes 耗尽)
  │           │
  │           └─ POST /ai/pipeline/auto/reclaim
  │                 └─ Server: running → pending（带上 error_message）
  │
  └─ 回收完成，退出 chunk 循环
```

## 十、异常状态恢复

每轮 Orchestrator 循环第一步执行 `_recover_stale()`，处理未正确完成的 jobs：

| 原状态 | 超时条件 | retry_count | 新状态 |
|---|---|---|---|
| running | `started_at < now() - 180min` | `< max_retries` | **pending**（retry_count +1） |
| running | `started_at < now() - 180min` | `>= max_retries` | **error**（标记 exhausted） |

> 恢复完成后，Orchestrator 会继续正常调度剩余的 pending jobs。
> 其他未被超时机制标记的 running jobs 由事件消费者正常处理。
