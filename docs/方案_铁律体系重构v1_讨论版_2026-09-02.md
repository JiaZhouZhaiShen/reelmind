## 二、定位与设计原则

**铁律 = 原则（指导 AGENT 怎么想、做什么、不做什么）**
**规范 = 执行细则（怎么做到铁律、边界在哪、怎么自查）**
**方案 = 具体问题解决（走"思考→方案→验证→确认"流程产出，不进铁律）**

三层不混：铁律和规范**不膨胀成解决方案库**。遇到具体 bug，走流程产出方案，而不是翻铁律找答案。

设计原则：

1. **简明**：CLAUDE.md 打开 30 秒内知道"我该按什么流程做事 + 有哪些铁律 + 去哪查细节"。铁律本体控制在 40 行内，每条一句话。
2. **指导性**：铁律只写原则与边界，不写实现细节、不写当前违规清单（会过期）。现状数据由脚本实时生成。
3. **可执行**：凡 grep 能查的硬规则全部进 `scripts/check.sh`，一处运行全量自查，可挂 pre-commit。
4. **成闭环**：铁律 ↔ 规范 ↔ 脚本 ↔ 修订记录 四者互相引用。改铁律必须同时改规范 + 脚本 + 记录，否则不算完成。

## 四、铁律本体（讨论稿）

> 原则：每条 = 编号 + 一句话 + 归属层。详细边界与检查方式见对应规范。

### 〇、工作流程铁律（总纲）

```
思考 → 方案 → 验证 → 确认 → 备份 → 修改 → 验证 → 删备份
```

- **R0.1 先验证再动手**：改前必须先 Read 文件确认基线；修 bug 先复现、改行为先确认、重构先确认逻辑。不验证就改 = 改坏了不负责。
- **R0.2 先方案后代码**：改动前先出方案，方案验证后确认，确认后备份再改。重大改动不确认不动手。
- **R0.3 备份铁律**：修改任何文件前备份到 `backups/{时间戳}_{描述}/`，修改后验证通过才删备份。备份完成后才允许修改。
- **R0.4 最小改动**：只做任务范围内的改动；不顺手修 bug、不顺手重构、不扩大范围。发现问题可以提出，不能擅自改。

### 一、后端铁律

- **R1.1 Server 只转发不做计算**：Server 不加载 AI 模型、不做 GPU 推理，AI 请求一律 HTTP 转发到 AI 容器。
- **R1.2 双数据库各司其职**：状态/元数据 → PG；AI 推理结果 → SQLite；向量 → PG(pgvector)。不存在一条数据双写。
- **R1.3 状态唯一写入口**：管道状态更新走 `job_helpers.set_job_status()`，禁止直接写 `ai_engine_jobs` / `processing_state`。
- **R1.4 接口职责单一**：api 文件 ≤500 行、职责单一优先于行数；超限即拆。
- **R1.5 后端不做渲染计算**：进度百分比、格式化给前端；业务聚合/状态推导可留后端。

### 二、前端铁律

- **R2.1 业务状态归 store**：API 返回的数据必须进 Zustand store；组件 `useState` 只存 UI 状态。
- **R2.2 子组件从 store 读数据**：不通过父组件穿透业务 props（>5 个即警告）。
- **R2.3 组件自包含三态**：每个组件自己处理 loading / error / empty，不依赖父组件。
- **R2.4 整页 ErrorBoundary**：每个路由页面外层必须包 ErrorBoundary。
- **R2.5 高频组件加 memo**：列表项、卡片、侧边栏等高频组件用 `React.memo`；全项目零 memo 是性能 bug。
- **R2.6 禁止空 catch**：每个 catch 必须有用户可见反馈；例外：`video.play()`、clipboard、SSE 解析。
- **R2.7 i18n 禁硬编码中文**：用户可见文本一律 `t('key')`。
- **R2.8 无死代码残留**：源码目录禁止 `.bak` / `.refactor-backup` / `.original` / 零引用页面。
- **R2.9 TS 严格模式**：`strict` + `noUnusedLocals` + `noUnusedParameters` 必须开启。

### 三、API 铁律

- **R3.1 API 按域拆分**：`api/` 按业务域拆文件，`client.ts` 只做 barrel 导出（≤50 行）。
- **R3.2 统一错误展示**：API 错误统一写入 store，页面顶部 `GlobalError` 展示。

### 四、调度铁律

- **R4.1 状态与结果分离**：`ai_engine_jobs.status` → PG；场景/字幕/标签/OCR → SQLite。
- **R4.2 展示依赖 results_ready**：前端判断"有没有场景"查 SQLite 实际记录数，不依赖引擎 status。

### 五、容器铁律

- **R5.1 AI / Orchestrator 必须 stateless**：容器删了重建不影响数据，模型权重预装镜像。
- **R5.2 禁止 docker.sock 挂载**：任何容器不得挂 `/var/run/docker.sock`。
- **R5.3 跨容器可追踪**：跨容器请求透传 `trace_id`，日志结构化写 stdout。

## 七、check.sh 设计（讨论稿）

**定位**：铁律中所有 grep 可查的硬规则，一处运行，输出✅/❌对照表。软规则（职责单一、三态自包含）不进脚本，靠 review。

```bash
#!/usr/bin/env bash
# 铁律硬规则检查  scripts/check.sh
# 用法: ./scripts/check.sh          # 全量
#       ./scripts/check.sh 前端      # 按层筛选
cd "$(dirname "$0")/.."

FAIL=0

rule() { # rule <编号> <描述> <测试命令>
  local id="$1" desc="$2"; shift 2
  if eval "$1" > /dev/null 2>&1; then
    printf "❌ %s %s\n" "$id" "$desc"; FAIL=1
  else
    printf "✅ %s %s\n" "$id" "$desc"
  fi
}

# --- 工作流程 ---
rule R0.3 "源码目录无 .bak 残留" \
  'find web/src server -name "*.bak*" -o -name "*.refactor-backup" -o -name "*.original" | grep -q .'

# --- 后端 ---
rule R1.1 "Server 无 AI 推理库" \
  'grep -rn "torch\|transformers\|model\.predict\|model\.encode" server/app/api/ | grep -q .'
rule R1.3 "无直接写 ai_engine_jobs" \
  'grep -rn "UPDATE.*ai_engine_jobs\|UPDATE.*processing_state" server/ | grep -v "alembic\|migration\|\.bak" | grep -q .'
rule R1.4 "后端 api 文件 ≤500 行" \
  'find server/app/api -name "*.py" -exec wc -l {} \; | awk "\$1 > 500" | grep -q .'

# --- 前端 ---
rule R2.6 "无空 catch" \
  'grep -rn "catch\s*()\s*=>\s*{}\|catch\s*{}" web/src/ | grep -v "video\.play\|clipboard\|node_modules" | grep -q .'
rule R2.7 "无硬编码中文" \
  'grep -rn "[\"'"'"']\{1\}[一-鿿].*["'"'"']" web/src/pages web/src/components web/src/stores | grep -v "i18n\|locales" | grep -q .'
rule R2.8 "前端源码无死代码残留" \
  'find web/src -name "*.bak*" -o -name "*.original" | grep -q .'
rule R2.9 "tsconfig 严格模式开启" \
  'grep -q "noUnusedLocals.*false\|noUnusedParameters.*false" web/tsconfig.json'
rule R2.5 "前端页面组件 ≤500 行" \
  'find web/src/pages -name "*.tsx" -exec wc -l {} \; | awk "\$1 > 500" | grep -q .'

# --- 容器 ---
rule R5.2 "无 docker.sock 挂载" \
  'grep -q "docker\.sock" docker-compose*.yml'

exit $FAIL
```

> 说明：以上为骨架，实际编写时用 `grep -q` 反转逻辑统一为"违规即 FAIL"；行数类用 `awk` 判断。可挂 git pre-commit + 手动运行。

## 八、闭环机制

**改铁律 = 四步闭环**，缺一不算完成：

```
改铁律（docs/铁律.md）
  ↓ 必须同步
改规范（docs/规范/XX.md）— 若规则涉及执行细则
  ↓ 必须同步
改脚本（scripts/check.sh）— 若规则可 grep 检查
  ↓ 必须同步
记修订（docs/铁律修订记录.md）— 日期 / 改动 / 验证结果 / 待办
```

- 每条铁律带引用：`R1.3 → [规范01] [check.sh]`，可追溯。
- 修订记录替代原 HANDOFF：HANDOFF 是 7 月的一次性执行快照，已过时；改造为持续维护的修订日志。
- 脚本是唯一"现状快照"来源：文档里不再写"当前违规"数字，改为 `./scripts/check.sh` 实时输出。
