## 一、背景与现状（实测）

- 仓库：`github.com/JiaZhouZhaiShen/reelmind`，Public，main 已同步，CI 全绿。
- 现状：4 个自建镜像全部本地构建，未发布到任何 registry：

| 服务 | Dockerfile | 当前本地镜像名 |
|------|-----------|----------------|
| reelmind-server | `server/Dockerfile.slim`（context 仓库根） | `reelmind/server-slim:latest` |
| reelmind-orchestrator | `server/orchestrator/Dockerfile` | `reelmind/orchestrator:latest` |
| reelmind-ai | `server/ai_service/Dockerfile` | `reelmind/ai:latest` |
| reelmind-nginx | `nginx/Dockerfile`（context ./nginx） | `reelmind/nginx:latest` |

- `postgres`/`redis` 用官方镜像，无需发布。
- 现状限制：新用户必须 `docker compose build`（AI 镜像含 torch/paddle，构建久、易失败），README 已如实标注"全部本地 build"。

## 二、目标

把 4 个自建镜像发布到 **GHCR（ghcr.io）**，让用户可选择"从 registry 拉取"或"本地 build"，最终降低体验门槛。

## 三、R0.5 边界

**做什么**：
1. `docker-compose.yml` 的 4 个服务镜像名改为环境变量可覆盖（默认保持当前本地名，向后兼容）。
2. 新增 GitHub Actions workflow `publish-images.yml`：tag `v*` 触发（或手动 dispatch），构建并推送 4 个镜像到 `ghcr.io/jiazhouzhaishen/*`，打版本 tag + `latest`。
3. `.env.example` 增加镜像覆盖变量（占位符，注释说明）。
4. README 与 `docs/en/PROJECT_GUIDE.md` 增加"从 GHCR 部署"章节，保留本地构建路径。
5. 首次发布后把 4 个 GHCR 包设为 Public（用户侧 UI/API 一步）。

**不做什么（本方案范围外）**：
- ❌ 不把 web/dist 打进镜像（v2 单独立项；registry 部署仍需先 `npm run build` 一次）。
- ❌ 不做 arm64 镜像（AI 镜像跨架构构建成本高，v2 再评估）。
- ❌ 不改业务代码、不改容器内部逻辑、不发布到 Docker Hub。
- ❌ 不切换仓库可见性、不处理旧 Release。

**涉及文件（主清单）**：
| 文件 | 动作 |
|------|------|
| `docker-compose.yml` | 4 个服务 `image:` 改为变量可覆盖 |
| `.github/workflows/publish-images.yml` | 新建（构建推送 GHCR） |
| `.env.example` | 补镜像覆盖变量说明 |
| `README.md` | 增 GHCR 部署章节 |
| `docs/必读_项目介绍与部署指南.md` | 同步中文部署说明（clone 段落与构建步骤的"本地 build"表述） |
| `docs/en/PROJECT_GUIDE.md` | 同步英文说明 |
| `docs/铁律修订记录.md` | 记录本次变更（收尾） |

**验收标准**：
1. `REELMIND_*_IMAGE=ghcr.io/...` 环境变量下 `docker compose pull && docker compose up -d` 可不执行本地 build 启动（web/dist 需先构建，见边界）。
2. 不设环境变量时行为与现在完全一致（本地 build，镜像名不变）。
3. Actions `publish-images` 在 tag 推送后全绿，ghcr 上 4 个包可见且为 Public。
4. `./scripts/check.sh` 13 项全绿。

## 四、关键设计

### 4.1 镜像命名与变量

Compose 的 `image:` 同时承担"本地 build 产物名"和"拉取名"。默认值保持现状：

```yaml
reelmind-server:
  image: ${REELMIND_SERVER_IMAGE:-reelmind/server-slim:latest}
reelmind-orchestrator:
  image: ${REELMIND_ORCHESTRATOR_IMAGE:-reelmind/orchestrator:latest}
reelmind-ai:
  image: ${REELMIND_AI_IMAGE:-reelmind/ai:latest}
nginx:
  image: ${REELMIND_NGINX_IMAGE:-reelmind/nginx:latest}
```

registry 用户设置（示例）：

```bash
export REELMIND_SERVER_IMAGE=ghcr.io/jiazhouzhaishen/reelmind-server:v9.26.0901
export REELMIND_ORCHESTRATOR_IMAGE=ghcr.io/jiazhouzhaishen/reelmind-orchestrator:v9.26.0901
export REELMIND_AI_IMAGE=ghcr.io/jiazhouzhaishen/reelmind-ai:v9.26.0901
export REELMIND_NGINX_IMAGE=ghcr.io/jiazhouzhaishen/reelmind-nginx:v9.26.0901
docker compose pull
docker compose up -d
```

> 说明：`docker compose pull` 会把 4 个镜像拉到本地；之后 `up` 不会触发 build。

### 4.2 发布触发

- 版本 tag（`v*`，如 `v9.26.0901`）→ 自动构建并推送 4 个镜像，打 `{tag}` 与 `latest`。
- **镜像 tag 保留 git tag 全名（含 `v` 前缀）**，例如 git tag `v9.26.0901` 对应镜像 `ghcr.io/jiazhouzhaishen/reelmind-server:v9.26.0901`；文档用户示例直接可用，无需去 `v`。
- `workflow_dispatch` → 手动对当前 main 构建（打 `latest` + `main-{sha}`），便于首次上线。
- 首次上线建议用 workflow_dispatch，避免直接改 tag 语义。
- 现有 `v0.1.0` / `v9.26.0901` 双 tag 说明：镜像只在 tag 推送或手动触发时构建；**不重推 `v0.1.0` 即不会为其重复构建**。统一发布口径从 `v9.26.0901` 起。

### 4.3 GHCR 可见性

- Actions 用 `GITHUB_TOKEN`（`packages: write`）推 ghcr，仓库 owner 推送自己的包无需额外 PAT。
- 推送后 GHCR 包默认继承仓库可见性策略；Public 仓库的容器包仍需在 **GitHub → 头像 → Packages**（或仓库 Packages 页）把 4 个包设为 Public，否则匿名拉取 403。方案收尾含此一步说明。

## 五、风险与决策点

| # | 风险/问题 | 处理 |
|---|-----------|------|
| D1 | AI 镜像构建体积大、耗时长（torch/paddle），GitHub runner 可能很慢或超时 | 仅 tag/workflow_dispatch 触发；layer cache；首次建议本机先 `docker compose build` 验证 Dockerfile 可构建再推 |
| D2 | registry 部署仍需本地 `npm run build`（web/dist 未入镜像） | v1 如实文档化；v2 立项把 web 构建产物打进 nginx/server 镜像，实现纯 `docker compose up` |
| D3 | arm64 支持 | 本方案只发 amd64；v2 评估 |
| D4 | GHCR 包名大小写 | 镜像路径统一小写 `ghcr.io/jiazhouzhaishen/*` |
| D5 | 回滚 | 旧版本镜像保留 tag；`docker compose` 指定旧 tag 即可回退 |

## 六、实施步骤（确认后按附件执行）

1. 备份涉及文件（R0.3）。
