## 1. 严重 BUG

### 1.1 `load_model` 端点使用未定义变量 → `NameError`（双重异常导致 500）

| 项目 | 内容 |
|------|------|
| **文件** | `server/ai_service/main.py` |
| **行号** | 551-572 |
| **严重度** | 🔴 **严重** — 前端加载模型必定触发 500 错误 |

**前端调用链路（已核实）：**

```
用户点击 "加载模型" 
  → web/src/components/ai/AIModelManage.tsx:64  handleModelAction(model, "load")
  → web/src/stores/ai.ts:185                    aiApi.loadAIModel(model)
  → web/src/api/ai.ts:86                        POST /api/ai/models/load/${modelName}
  → NGINX 路由到 server
  → server/app/api/ai/models.py:52              httpx.post("http://reelmind-ai:2589/pipeline/load/{model_name}")
  → server/ai_service/main.py:551               @app.post("/pipeline/load/{model_name}")  ← BUG 在此
```

**问题代码：**

```python
@app.post("/pipeline/load/{model_name}")
async def load_model(model_name: str):        # ← 参数是 model_name
    if model_name not in _model_states:
        raise HTTPException(status_code=404, detail=f"Unknown model: {model_name}")

    success = _load_model_instance(model_name)  # ← 模型加载成功

    # Delete PG engine jobs so pipeline does not skip re-processing
    try:
        from models.db import get_pg_session
        from sqlalchemy import text
        pg = get_pg_session()
        pg.execute(text("UPDATE ai_engine_jobs SET status = :s, ... WHERE media_id = :mid"),
                   {"s": "pending", "mid": video_id})  # ← ① 第一次 NameError（被 except 捕获）
        pg.commit()
        pg.close()
        logger.info("Reset PG engine jobs to pending for video %s", video_id)
    except Exception as e:
        logger.warning("Failed to delete PG engine jobs for %s: %s", video_id, e)
        # ← ② 第二次 NameError（UNCAUGHT!）→ 端点返回 500
```

**根因**：`video_id` 在函数作用域内从未定义。**已确认复制源是同文件第 868 行的 `reset_asset` 端点**——两段 SQL 语法完全一致（连注释都一样），在 `reset_asset` 中 `video_id` 是函数参数所以合法，但在 `load_model` 中被遗漏未改名。更严重的是，`video_id` 在 **两处** 被使用：`pg.execute()` 中的 NameError 被 `except Exception` 捕获，但 `except` 块内的 `logger.warning(...)` 再次引用 `video_id`，导致**第二个 NameError 未被任何 try/except 包裹**，直接传播为 500 Internal Server Error。

> **补充发现**：同文件 `reset_asset`（805-875行）和 `load_model`（551-575行）中有**完全相同的 PG 作业重置 SQL 代码块**。应抽取为公共函数 `_reset_pg_jobs_for_video(video_id)` 以消除重复（参见新增 Bug 3.7）。

**影响**：
- 用户每次通过前端 UI 加载模型时，模型实际已加载到 GPU，但端点返回 500
- 前端 `handleModelAction` 捕获错误后显示 "Model action failed" 提示
- 错误信息中不包含有效上下文，排查困难
- PG 引擎作业状态未被重置，可能影响后续批处理逻辑
- `pg.close()` 未执行 → 数据库连接泄漏

**修复方案**：

> **决策结论：采用方案 A（直接删除）**。经完整调用链核实——前端 `AIModelManage.tsx` → `stores/ai.ts` → `api/ai.ts` → Server proxy → AI Service——`load_model` 端点的**所有调用方均未传入 `video_id`**。这是一个全局模型管理操作（将模型加载到 GPU），与任何特定视频无关。PG engine jobs 重置属于 `reset_asset` 端点的职责，不应隐含在模型加载中。

方案 A — 删除无效代码块：
```python
@app.post("/pipeline/load/{model_name}")
async def load_model(model_name: str):
    if model_name not in _model_states:
        raise HTTPException(status_code=404, detail=f"Unknown model: {model_name}")
    success = _load_model_instance(model_name)
    return {"status": "ok" if success else "error", "model": model_name, "loaded": success}
```

> **不再推荐方案 B**：方案 B 需给 `load_model` 添加 `video_id` 参数，但该端点本质是模型管理而非作业管理，引入 `video_id` 会导致接口语义混乱。如需重置作业，应直接调用 `reset_asset` 端点。

### 1.2 裸 `except:` 吞没系统级异常

| 项目 | 内容 |
|------|------|
| **文件** | `server/ai_service/main.py` |
| **行号** | 316 |
| **严重度** | 🔴 **严重** — 阻止进程正常退出 |

**问题代码：**

```python
                try:
                    asset = pg.query(Asset).filter(Asset.id == _uuid.UUID(vid)).first()
                    if asset and os.path.isfile(str(asset.original_path)):
                        assets.append(asset)
                except:       # ← 裸 except: 会捕获 KeyboardInterrupt, SystemExit!
                    pass
```

**根因**：Python 中裸 `except:` 会捕获包括 `KeyboardInterrupt`、`SystemExit`、`MemoryError`、`GeneratorExit` 在内的所有异常。当运维人员按 `Ctrl+C` 或进程管理器发送 SIGTERM 时，异常会被此 `except` 吞没，进程无法正常退出。

**影响**：
- `KeyboardInterrupt`（Ctrl+C）被吞没 → 进程卡住，只能 `kill -9`
- `SystemExit`（`sys.exit()` 调用）被吞没 → 优雅退出逻辑失败
- 调试极其困难，因为所有错误都在无日志的情况下被丢弃

**修复方案**：
```python
                except Exception:          # 只捕获普通异常
                    # 至少记录一下，便于排查
                    logger.debug("Skipping asset %s (not found or missing file)", vid)
```

### 2.1 SQL 注入模式 — 字符串拼接 SQL

| 项目 | 内容 |
|------|------|
| **文件** | `server/app/api/assets.py` |
| **行号** | 379-387 |
| **严重度** | 🟠 **高** — 虽当前输入可控，但模式极其危险 |

**问题代码：**

```python
def _enrich_ai_flags(items: list[AssetRead]) -> None:
    ids = [str(item.id) for item in items]
    _ai = get_ai_session()
    yolo_rows = _ai.execute(_sa_text(
        "SELECT DISTINCT s.video_id FROM scenes s JOIN scene_tags st ON st.scene_id = s.id "
        "WHERE s.video_id IN ({0})".format(",".join('"' + x + '"' for x in ids))
    )).fetchall()
    ocr_rows = _ai.execute(_sa_text(
        "SELECT DISTINCT s.video_id FROM scenes s JOIN scene_ocr so ON so.scene_id = s.id "
        "WHERE s.video_id IN ({0})".format(",".join('"' + x + '"' for x in ids))
    )).fetchall()
```

**根因**：使用 Python `.format()` 方法将字符串直接拼接到 SQL 中。即使当前 `ids` 的数据源是数据库中的 UUID（`str(item.id)`），这种模式仍是 SQL 注入漏洞的教科书案例。一旦数据源发生变化（如接收用户输入），就会成为真正的安全漏洞。

**影响**：
- 当前：由于输入是内部 UUID，风险可控
- 未来：如果此函数被重用以处理外部输入，立即变成高危 SQL 注入
- 代码审查工具（如 Bandit）会标记此行为安全缺陷

**修复方案**（使用 SQLAlchemy 参数化查询）：

```python
from sqlalchemy import bindparam

yolo_rows = _ai.execute(
    _sa_text("SELECT DISTINCT s.video_id FROM scenes s JOIN scene_tags st ON st.scene_id = s.id "
             "WHERE s.video_id IN :ids").bindparams(bindparam('ids', expanding=True)),
    {"ids": ids}
).fetchall()
```

> 注意：`expanding=True` 参数需要 SQLAlchemy 1.4+ 版本。

或者改用 ORM 风格（更安全）：
```python
from app.models.ai import Scene, SceneTag

yolo_ids = set(
    row[0] for row in
    _ai.query(Scene.video_id)
       .join(SceneTag, SceneTag.scene_id == Scene.id)
       .filter(Scene.video_id.in_(ids))
       .distinct()
       .all()
)
```

> **决策结论：采用 bindparam 方案（6.3 节）**。该项目使用 SQLAlchemy 2.0.31，`expanding=True` 完全受支持。ORM 方案需额外导入模型类到 `assets.py`——该模块只做数据查询，引入模型依赖会破坏分层。bindparam 改动最小、语义最清晰：参数化 SQL 等价于原来的 `.format()` 拼接方式，只是消除了注入风险。

### 2.2 数据库会话资源泄漏（异常路径未关闭）

| 项目 | 内容 |
|------|------|
| **文件** | `server/ai_service/main.py` |
| **行号** | 300-320 |
| **严重度** | 🟠 **高** — 连接池耗尽 |

**问题代码：**

```python
            pg = get_pg_session()
            assets = []
            for vid in video_ids:
                try:
                    asset = pg.query(Asset).filter(Asset.id == _uuid.UUID(vid)).first()
                    if asset and os.path.isfile(str(asset.original_path)):
                        assets.append(asset)
                except:
                    pass
            pg.close()
```

**根因**：如果 `pg = get_pg_session()` 成功，但在 `for` 循环之前发生异常（例如 `video_ids` 为 `None` 导致迭代失败），则 `pg.close()` 永远不会执行。此外，如果 `pg.query()` 本身抛出异常（而非 `for` 循环内的异常），会话也可能泄漏。

**影响**：
- 长期运行后数据库连接池耗竭
- PostgreSQL 出现 `too many clients` 错误
- 影响整个应用的数据访问

**修复方案**：

```python
            pg = get_pg_session()
            try:
                assets = []
                for vid in video_ids:
                    try:
                        asset = pg.query(Asset).filter(Asset.id == _uuid.UUID(vid)).first()
                        if asset and os.path.isfile(str(asset.original_path)):
                            assets.append(asset)
                    except Exception:
                        logger.debug("Skipping asset %s", vid)
            finally:
                pg.close()
```

> 更好的做法是将 `get_pg_session()` 改造为 context manager，彻底消除手动管理。

### 2.3 Daemon 线程强制终止 → 资源泄漏 + 数据不一致

| 项目 | 内容 |
|------|------|
| **文件** | `server/ai_service/main.py` |
| **行号** | 460-461 |
| **严重度** | 🟠 **高** — 数据一致性风险 |

**问题代码：**

```python
    task_thread = threading.Thread(
        target=_run_pipeline_task,
        args=(task_id, task_params, progress_callback),
        daemon=True        # ← daemon 线程在进程退出时被强制终止
    )
    task_thread.start()
```

**根因**：Python 的 daemon 线程在进程退出时会被**立即强制终止**，不执行任何 `finally` 块或清理代码。

**影响**：
- 数据库事务未提交/回滚 → 数据不一致（`ai_engine_jobs` 状态可能永远卡在 `"running"`）
- GPU 显存未释放 → 需要手动重启 AI 容器
- `_task_cancel_events` 字典中存在僵尸条目 → 内存泄漏
- 子进程（ffmpeg 等）可能变成孤儿进程

**修复方案**：

方案 A — 注册退出清理（最小改动）：
```python
import atexit
import signal

_active_threads: list[threading.Thread] = []

def _cleanup_threads():
    for t in _active_threads:
        if t.is_alive():
            # 设置取消事件
            cancel_event.set()
            t.join(timeout=30)

atexit.register(_cleanup_threads)
```

方案 B — 使用非 daemon 线程 + 可控生命周期：
```python
task_thread = threading.Thread(
    target=_run_pipeline_task,
    args=(task_id, task_params, progress_callback),
    daemon=False
)
task_thread.start()
_active_threads.append(task_thread)
```

方案 C — 使用 `multiprocessing.Process`（长期推荐）：
```python
process = multiprocessing.Process(
    target=_run_pipeline_task,
    args=(task_id, task_params, progress_callback)
)
process.start()
```

> **决策结论：采用方案 B（非 daemon + 线程追踪，6.4 节）**。方案 A（atexit）对 SIGKILL 无防护——Docker 容器停服时 `atexit` 注册函数不一定执行。方案 C（`multiprocessing.Process`）变更范围太大：需处理 `_task_cancel_events`、`_task_progress` 等线程间共享状态的序列化问题，还有 GPU 上下文跨进程传递。方案 B 只需改 `daemon=False` + 追踪列表，改动最小、直接消除数据不一致风险。

### 3.2 AI Service 与 Orchestrator 联合缺陷：GPU 健康检查失败 → 误判为空闲

| 项目 | 内容 |
|------|------|
| **文件** | `server/ai_service/main.py` + `server/orchestrator/main.py` |
| **行号** | ai_service:441-442, orchestrator:124 |
| **严重度** | 🟡 **中** — 调度决策错误（假阴性） |

**问题描述**：这是一个跨两个服务的联合缺陷，单看任一端都不明显。

**缺陷 1 — AI Service（441-442行）health 端点**：

```python
    try:
        import torch
        if torch.cuda.is_available():
            gpu = True
            free_bytes, total_bytes = torch.cuda.mem_get_info()
            total_gb = round(total_bytes / 1073741824, 2)
            total_used_gb = round((total_bytes - free_bytes) / 1073741824, 2)
    except Exception:
        pass    # ← GPU 查询异常时，total_gb 保持初始值 0，无日志
    return {
        "status": "ok",
        "gpu": gpu,
        "total_gb": total_gb,        # ← 异常时为 0
        "total_used_gb": total_used_gb,
    }
```

**缺陷 2 — Orchestrator（124行）GPU 判断**：

```python
    total_gb = body.get("total_gb", 0) or 1    # ← or 1 将 0 掩码为 1
    total_used = body.get("total_used_gb", 0)
    total_pct = total_used / total_gb * 100      # ← 0/1*100 = 0%
    if total_pct > gpu_threshold:
        return False
```

**缺陷链条**：
1. AI Service GPU 查询异常 → `except Exception: pass` → `total_gb=0`
2. Orchestrator 收到 `total_gb=0` → `or 1` 变成 `1`
3. `total_used / 1 * 100 = 0%` → 认为 GPU 完全空闲
4. Orchestrator 继续调度 → 实际 GPU 可能正忙/驱动故障

这不是 ZeroDivisionError（`or 1` 已保护），而是**假阴性调度错误**——GPU 不可用时被误判为空闲。

**修复方案**：

AI Service（441-442行）— 记录日志但保持返回 0（orchestrator 需要区分"健康检查失败"）：
```python
    except Exception as e:
        logger.warning("GPU health check failed: %s", e)
        # 保持 total_gb=0, total_used_gb=0 — orchestrator 会识别
```

Orchestrator（124行）— 将 `or 1` 掩码改为显式跳过：
```python
    total_gb = body.get("total_gb", 0)
    if total_gb <= 0:
        logger.warning("GPU health returned total_gb=%s, skipping this cycle", total_gb)
        return False
    total_used = body.get("total_used_gb", 0)
    total_pct = total_used / total_gb * 100
    if total_pct > gpu_threshold:
        ...
```

> **变更说明**：`or 1` 是原始代码防止除零的保护，但它把错误信息也掩码了。改为显式检查：如果 health 端点返回无效值，宁可跳过一轮也不误判空闲。

### 3.3 Pipeline 端点缺少输入验证

| 项目 | 内容 |
|------|------|
| **文件** | `server/ai_service/main.py` |
| **行号** | 201-207 |
| **严重度** | 🟡 **中** — 潜在 DoS |

**前端调用验证**：
- `web/src/api/ai.ts:201` `startManualPipeline()` → POST 空 body，后端硬编码 `video_ids=[]`
- `web/src/api/ai.ts:251` `startSinglePipeline(videoId)` → POST `{video_ids: [videoId]}`
- 前端正常使用时发送的 payload 均在安全范围内，不会触发 DoS
- 风险在于**直接对后端 API 的恶意调用**（绕过前端），属于防御纵深问题

**问题代码：**

```python
class StartRequest(BaseModel):
    limit: int = 10
    video_ids: list[str] | None = None
    engines: list[str] | None = None
    task_label: str = "manual"
    filters: dict | None = None
```

- `limit` 无上限 → 传入 `999999` 可耗尽内存
- `video_ids` 无长度限制 → 可传入百万级列表
- `engines` 无白名单校验 → 可传入任意字符串

**修复方案**：

```python
VALID_ENGINES = frozenset({'scene', 'yolo', 'ocr', 'clip', 'transcript', 'diarization'})

class StartRequest(BaseModel):
    limit: int = Field(default=10, ge=0, le=10000)
    video_ids: list[str] | None = Field(default=None, max_length=10000)
    engines: list[str] | None = Field(default=None, max_length=6)
    task_label: str = "manual"
    filters: dict | None = None

    @field_validator('engines')
    @classmethod
    def validate_engines(cls, v: list[str] | None) -> list[str] | None:
        if v is None:
            return v
        invalid = set(v) - VALID_ENGINES
        if invalid:
            raise ValueError(f"Unknown engines: {invalid}. Valid engines: {VALID_ENGINES}")
        return v
```

### 3.4 前端 `fetch` 无网络级错误处理

| 项目 | 内容 |
|------|------|
| **文件** | `web/src/api/base.ts` |
| **行号** | 23 |
| **严重度** | 🟡 **中** — 用户体验差 |

**问题代码：**

```typescript
  const res = await fetch(url, { ... });
```

如果 `fetch` 本身失败（DNS 解析失败、连接拒绝、超时），错误会直接以未捕获 rejection 的形式向上传播。虽然当前所有 stores 调用方都有 `try/catch`，但如果将来有新组件直接调用而未处理，会导致问题。

**修复方案**：

```typescript
  try {
    const res = await fetch(url, { ... });
    if (!res.ok) {
      const body = await res.json().catch(() => ({}));
      throw new Error(body.detail || `HTTP ${res.status}: ${res.statusText}`);
    }
    return res.json();
  } catch (err) {
    if (err instanceof TypeError && err.message === 'Failed to fetch') {
      throw new Error('无法连接到服务器，请检查网络或服务器状态');
    }
    throw err;
  }
```

```python
# server/app/models/ai.py — 新增
from contextlib import contextmanager

@contextmanager
def ai_session(db_path=None):
    """AI session context manager — 自动关闭，包括异常路径。"""
    session = get_ai_session(db_path)
    try:
        yield session
    finally:
        session.close()
```

**调用方替换**（以 `search.py` 为例）：

```python
# 修改前 — 异常路径泄漏 session
_ai = get_ai_session()
try:
    rows = _ai.execute(text("SELECT ...")).fetchall()
except Exception:
    return []
_ai.close()

# 修改后 — with 块自动清理
with ai_session() as _ai:
    rows = _ai.execute(text("SELECT ...")).fetchall()
```

> **变更说明**：原 `get_ai_session()` 保持不变（向后兼容），新增 `ai_session()` 作为推荐用法。`search.py` 中 6 处 session 使用点逐一替换为 `with ai_session() as _ai:` 模式。具体实现见 6.14 节。

    limit: int = Field(default=10, ge=0, le=10000)
    video_ids: list[str] | None = Field(default=None, max_length=10000)
    engines: list[str] | None = Field(default=None, max_length=6)
    task_label: str = "manual"
    filters: dict | None = None

    @field_validator('engines')
    @classmethod
    def validate_engines(cls, v: list[str] | None) -> list[str] | None:
        if v is None:
            return v
        invalid = set(v) - VALID_ENGINES
        if invalid:
            raise ValueError(f"Unknown engines: {invalid}. Valid engines: {VALID_ENGINES}")
        return v
```

> **变更说明**：
> 1. `limit` 限制 0–10000
> 2. `video_ids` 限制最大 10000 条
> 3. `engines` 限制最大 6 个，且白名单校验
> 4. 需要在文件头部添加 `from pydantic import BaseModel, field_validator, Field`

from contextlib import contextmanager

@contextmanager
def ai_session(db_path=None):
    """AI session context manager — 自动关闭，包括异常路径。"""
    session = get_ai_session(db_path)
    try:
        yield session
    finally:
        session.close()
```

**`server/app/api/search.py` — 替换全部 6 处 session 使用点**：
